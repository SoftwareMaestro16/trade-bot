# TEST-PLAN — стратегия тестирования (STLC)

Версия 1.0 · Фаза 0 · входные документы: [SRS.md](SRS.md), [ARCHITECTURE.md](ARCHITECTURE.md), [RISK-REGISTER.md](RISK-REGISTER.md)

STLC идёт параллельно SDLC, не после (бриф, раздел 4). Этот документ закрывает шаги 1–2 STLC — Requirement Analysis и Test Planning. Шаг 3 (Test Case Development) — в [TEST-CASES.md](TEST-CASES.md).

---

## 1. Requirement Analysis — что тестируемо

| Категория требований | Тестируемо автоматически | Тестируемо только вручную/на testnet |
|---|---|---|
| Чистые функции (`strategy/`, сайзинг, нормализация фандинга, расчёт плеча) | Да — unit, включая property-based | — |
| Проверки `risk/` (вето, пороги) | Да — unit на моках | — |
| Идемпотентность, резолв неопределённого состояния ордера | Да на моках; поведение биржи (реальные `retCode`, окна ретеншна `orderLinkId`) — только testnet | Реальные тайминги Bybit |
| WS-реконнект, дедупликация филлов | Да на моках (мок-сервер эмулирует разрыв, дубль, задержку) | Реальная частота реконнектов — только длительное наблюдение |
| Kill switch, все три уровня | Частично на моках (уровень 1 внутри процесса), полностью — только на testnet с реальным процессом | Ручные тренировки (RR-38) — только вручную |
| Восстановление после SIGKILL с открытой позицией | Нет на моках (требует реального процесса и реальной ОС) | testnet, обязательный exit criterion Фазы 3 |
| Прибыльность стратегии | **Нет вообще** — ни один автотест не отвечает на этот вопрос | Только paper trading на данных mainnet (Фаза 2) |
| Реальные лимиты API, коды ошибок, поведение при maintenance | Нет | testnet + документация, с явными открытыми вопросами (RISK-REGISTER.md, раздел «Открыто») |

Прямое следствие таблицы: **testnet проверяет корректность кода, не прибыльность стратегии** (бриф, раздел 4) — это архитектурное разделение, а не примечание. Тест «стратегия зарабатывает» не существует в этом плане и не должен быть написан — на него отвечает только Фаза 2.

## 2. Test Planning — три контура окружения

| Контур | Что в нём проверяется | Что в нём проверить нельзя |
|---|---|---|
| **Mocks (unit)** | Логика: сайзинг, риск-вето, машина состояний, резолв неопределённости, обработка ошибок биржи, дедупликация. Быстро, детерминированно, в CI на каждый push | Реальное поведение Bybit — коды ошибок, тайминги, лимиты — только то, что замокано |
| **Bybit testnet (integration/system)** | Реальное размещение ордеров, реальные `retCode`, реальное поведение `orderLinkId`, реальный WS, восстановление после `kill -9` | Прибыльность — на testnet нет реальной ликвидности, funding не отражает настоящую экономику |
| **Публичные данные mainnet (paper trading)** | Прибыльность стратегии на реальных рыночных данных, виртуальные сделки | Поведение исполнения — сделки виртуальные, реальных `retCode` и партиального филла здесь не бывает |

Ни один контур не заменяет другой. Фаза 3 без Фазы 2 проверила бы код, но не ответила бы «работает ли стратегия». Фаза 2 без Фазы 3 не поймала бы ни одного отказа из тира 1 RISK-REGISTER.md.

## 3. Entry / Exit criteria по фазам

Дублирует и детализирует раздел 8 брифа с привязкой к тестовым артефактам.

### Фаза 1 — сборщик данных

**Entry:** `ARCHITECTURE.md` закрыт, схема БД для market-data готова, `exchange/` умеет читать публичные эндпоинты.
**Exit:** две недели непрерывного сбора без пропусков (FR-109 измеряет это явно, не предполагает). Ответ на вопросы: сколько монет в сутки дают funding выше порога окупаемости (RISK-REGISTER.md FM-01: на момент анализа — ноль по строгому порогу; Фаза 1 обязана дать актуальную цифру), как долго держится, коррелирует ли с OI и ликвидациями.
**Тесты, обязательные к этому моменту:** все unit-тесты нормализации фандинга (RSK-25), детекции смены интервала (RSK-26), полный property-тест сайзинга по реальному снапшоту instruments-info (TEST-CASES.md №1).

### Фаза 2 — paper trading

**Entry:** Фаза 1 закрыта. `strategy/`, `risk/` реализованы и покрыты unit-тестами полностью (NFR-13).
**Exit:** две недели, виртуальный P&L положительный после всех комиссий (включая заимствование — RR-25a), ни одного решения без объяснимого лога (FR-202). Поправка на реальность из брифа: живой результат будет на 30–50% хуже бумажного — это условие входа в Фазу 3, не пожелание.
**Тесты, обязательные к этому моменту:** экономические тесты RISK-REGISTER FM-01/07/09 (№49, №50 из банка ниже), тест на отсутствие направленного сигнала в решениях (ручной аудит логов, FR-202).

### Фаза 3 — testnet, исполнение

**Entry:** Фаза 2 закрыта. Весь код `execution/`, `killswitch/`, `reconciliation/` реализован.
**Exit:** неделя без рассинхронизации состояния; бот корректно поднимается после принудительного убийства процесса с открытой позицией; kill switch проверен вручную не менее 5 раз в разных состояниях (RR-38), включая позицию, превышающую `maxMktOrderQty` (RISK-REGISTER FM-31).
**Тесты, обязательные к этому моменту:** весь негативный набор раздела 4 ниже, полный given/when/then банк из TEST-CASES.md — это и есть содержание Фазы 3, не последующая проверка.
**Дополнительно закрываются открытые вопросы** из RISK-REGISTER.md («Открыто: измерить на testnet») — без ответов на них Фаза 4 не начинается, поскольку от них зависят конкретные пороги (rate limiter, `FUNDING_ENTRY_BLACKOUT_SECONDS`, режим маржи).

### Фаза 4 — mainnet, минимальный размер

**Entry:** Фазы 1–3 закрыты по exit criteria, зафиксированным в `PHASE-LOG.md`. Сумма Фазы 4 подтверждена владельцем (OPEN-01/OPEN-02 SRS).
**Exit:** месяц, расхождений нет, P&L соответствует расчётному.
**Тесты:** ежедневная сверка (FR-304) — уже не тест, а штатная операция, но её отсутствие в первый же день само является провалом exit criterion.

## 5. Уровни тестирования

**Unit** — чистые функции и модули на моках, CI на каждый push, обязательное покрытие для всего денежного (NFR-13).
**Integration** — testnet, реальные вызовы API, ручной или полуавтоматический запуск в рамках Фазы 3.
**System** — полный контур: trader + killswitch-listener + watchdog + БД, тесты вида «убить процесс», «отключить БД», «заблокировать файрволом api.bybit.com».
**Acceptance** — владелец, глядя на месяц paper trading, говорит «да, edge есть» (бриф, раздел 4). Формальный тест этому не соответствует — это решение человека на основе метрик Фазы 2.

## 6. Test Cycle Closure — критерий для каждой фазы

Переход на следующую фазу не происходит без записи в `PHASE-LOG.md`, содержащей: что покрыто, что нет, какие риски остались приняты осознанно (со ссылкой на конкретный `AR-nn` из RISK-REGISTER.md, не общими словами). Это прямое требование брифа (раздел 4, п.6) — без этого документа переход на боевые деньги не происходит вообще, независимо от того, насколько хорошо выглядят метрики.
