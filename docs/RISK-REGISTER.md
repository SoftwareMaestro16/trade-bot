# RISK-REGISTER — реестр рисков

Версия 1.0 · Фаза 0 · синтез 2026-08-05 · вход: 11 независимых исследований + враждебная фактчек-верификация каждого

Каждая строка отвечает на вопрос брифа: **какой конкретный механизм в коде ловит этот риск.** Где механизма нет — риск помечен ACCEPTED с числовым потолком, а не подразумевается.

Легенда вероятности для одиночного разработчика с малым счётом: **[П]** почти наверняка в первый месяц · **[В]** вероятно в первый год · **[Р]** редко, но катастрофично · **[Т]** теоретическое на малом счёте — записать, не проектировать под это сейчас.

Идентификаторы: `FM-nn` — режим отказа, `RSK-nn` — тестируемое требование (дополняет `RR-nn`/`FR-nn` из [SRS.md](SRS.md)), `AR-nn` — принятый риск (нумерация продолжает `AR-01..06` из SRS §6, старые AR-01..06 из SRS переносятся сюда как AR-S1..S6 без потери).

## ТИР 0 — Экономика: здесь стратегия либо есть, либо её нет

Всё в этом тире — **[П]**, ущерб — весь смысл проекта, и отказ **не бросает исключение**: это ровно снижающаяся кривая капитала, которую два месяца принимают за нормальную дисперсию.

### FM-01. Порог входа ниже точки безубыточности — угроза #1

Формула Bybit `F = clamp[P + clamp(I−P, ±0.05%), cap, floor]` при интервальной ставке `I = 0.01%/8h` **прибивает ставку ровно к 0.01%**, когда |premium| < 0.05%/8h. Измерено: 29 из 33 ликвидных spot-paired символов имели максимум ровно +0.0100%/8h за 66 дней; 41–49% всех интервалов BTC/ETH/SOL за 3.6 года — на этом уровне или выше.

Бэктест на реальной истории, вход ≥0.01% / выход <0: BTC 130 эпизодов, win-rate 8%, **−15.4% нотионала**; ETH 140/10%/−18.3%; SOL 240/4%/−45.7%. Медианный эпизод собирает 0.015–0.045% брутто против 0.31–0.50% round-trip.

**Механизм:** два чистых гейта в `strategy/`, оба unit-tested. (а) `isPremiumDriven(symbol)` — отказ, если premium index (нормализованный к 8h) не превышает +0.05%: ставка на полу **не является** сигналом, это артефакт клампинга. (б) `expectedGross = r8h × expectedHoldIntervals >= K × C_total`, K по умолчанию **2.0**. Дефолт порога в конфиге — **0.020%/8h, никогда 0.010%**. Регрессионный тест на сохранённой истории, который должен пиннить: суммарный net P&L > 0 при 0.020% и < 0 при 0.010% (тест-кейс №49 в [TEST-CASES.md](TEST-CASES.md)) — **PENDING, не реализован**: `test/risk/economics.test.ts` сегодня юнит-тестирует только `checkEntryThreshold`/`isPremiumDriven` на синтетических фикстурах, а сам TEST-CASES.md фиксирует кейс №49 как требующий «недель реальных данных, которых пока физически нет».

Это уточняет правило входа из [PARAMS-CONSERVATIVE.md](PARAMS-CONSERVATIVE.md) §5 («окупаемость за ≤3 суток» ⇒ уже ≈0.034%/8h для 8-часовых символов) — правило совместимо и даже строже рекомендации, но `isPremiumDriven` в исходном профиле не было. **Добавить.**

### FM-02. Модель издержек неверна: хардкод комиссий, симметричный slippage, maker-иллюзия

**На VIP0 spot maker = spot taker = 0.1000%.** Дисконт есть только на перпе (0.055%→0.020%), то есть весь достижимый выигрыш от лимитного исполнения — 7bp из 31bp круга, а платой служит висящая нога — ровно leg-risk, который запрещает RR-10 (SRS). Exit-нога систематически хуже entry-ноги в стакане (LINK $25k: sell 10.20bp против buy 5.36bp), а важные выходы (kill switch, флип фандинга) коррелируют с тонкой книгой. `cumExecFee` не несёт валюту — читать `cumFeeDetail` и `feeCurrency`.

**Механизм:** ставки комиссий — обязательные аргументы функции прибыльности без дефолтов, из `GET /v5/account/fee-rate` при старте и ежедневно. Асимметричные множители slippage: entry ×1.5, exit ×3.0 к p10-худшему сохранённому стакану, плюс пол +2bp/ногу при spot spread >3bp.

### FM-03. Ликвидность меряется по perp-книге, а связывающее ограничение — spot-книга

SOLUSDT: perp ask depth $52.9M против spot ask depth **$3.80M**. LINKUSDT spot ask $0.53M, WLDUSDT $0.39M, STRKUSDT $0.15M. Четырёхногий slippage на $25k: LINK 19.3bp (15.6 из них — spot), STRK 117.1bp. На $100k STRK spot buy сам исчерпывает 200 уровней книги. Скрин по perp-глубине занижает round-trip в 3–5 раз.

**Механизм:** `market-data/` хранит полную лестницу `GET /v5/market/orderbook?category=spot&limit=1000` для каждого кандидата. `C_total` — ladder-walk на **обеих** книгах против `mid`. Вход отклонён при исчерпании глубины — явная ошибка, не частичная оценка (тест-кейс №51).

### FM-04. `fundingInterval` — не 8 часов, меняется на лету, отсутствует в сырой истории

Интервал в минутах: живой снимок — 408 перпов на 240 мин, 344 на 480, 2 на 60 (COTIUSDT, ERAUSDT). **Bybit автоматически переключает символ на часовой сеттлмент, когда ставка упирается в свой кап** — «typically within four minutes, without prior notice» — и переключение случается именно на экстремальных ставках, то есть там, где бот хочет торговать. `GET /v5/market/funding/history` не возвращает поле интервала: в датасете есть 26 подряд 120-минутных сеттлментов SOLUSDT — наивная агрегация «%/8h» по сырой истории занижена, и искажение концентрируется на самых доходных символах.

**Механизм:** интервал — live-поле с TTL в один цикл, никогда константа. Единственная функция нормализации `r8h = rate × 480 / interval_minutes` на границе `market-data/`. Историческая агрегация выводит интервал из дельты таймстампов с ассертом `delta ∈ {60,120,240,480}` — иначе громкий отказ. **Смена интервала на удерживаемом символе — триггер kill-switch уровня 2** (`INTERVAL_CHANGE_ACTION=exit`). Это дополняет FR-101/RR-25 SRS явным новым триггером.

### FM-05. Predicted funding ≠ settled; TWAP-веса делают ранний вход бессмысленным

Average Premium Index взвешен по времени: последний час несёт ~23% веса, первый ~0.4%. Чтение «0.05%» на 30-й минуте 8-часового интервала построено на минимально весомой выборке — тяжёлые последние часы утянут его к 0.005%.

**Механизм:** предикат входа — функция от `minutes_remaining`, отказ раньше `(interval − W)`. Плюс требование персистентности: ставка выше порога N подряд сеттлментов по сохранённой истории, не разовое чтение.

### FM-06. Basis (perp−spot) — член P&L того же порядка, что весь доход от фандинга, и не учтён

Живой срез 293 spot-paired перпов: медиана −9.6bp, p5 −31.4bp; на ликвидном подмножестве p95 = −2.9bp — **почти каждый ликвидный перп торгуется ниже спота**. Вход при −9.6bp / выход при 0 = 0.096% (26–29% всего комиссионного счёта). Структурно хуже: правило выхода «фандинг стал отрицательным» = «перп ушёл в дисконт» ⇒ **выход систематически совпадает с неблагоприятным basis**. Отдельно: `lastPrice`/`indexPrice`/`markPrice`/spot mid — четыре разных числа; фандинг и ликвидация считаются от `markPrice`.

**Механизм:** `basisEntry` входит в `C_total`; вето при `basisEntry < minEntryBasisBp` (дефолт 0). Все маржинальные и доходные расчёты — от `markPrice`; `lastPrice` только для оценки филла.

### FM-07. 25%-правило и квалифицирующаяся вселенная арифметически несовместимы

Живой срез: 33 символа проходят perp≥$5M И spot≥$1M; из них 13 на ≥0.010%/8h; **ноль на ≥0.020%/8h** — единственном пороге, бэктестящемся положительно. Частота на этом пороге: 5 эпизодов/год на BTC, 5 на ETH, 11 на SOL. Правило 25% требует ≥4 одновременных позиций для полного развёртывания капитала — при такой частоте это структурно невозможно большую часть года. Выбор: капитал простаивает, либо фильтр ослабляется в неликвидный хвост (round-trip 117bp).

**Механизм:** `strategy/` возвращает три именованных поля — `yieldOnLegNotional`, `yieldOnGrossNotional`, `yieldOnEquity` — «годовая доходность» одним голым числом запрещена. Пороги `risk/` сравниваются с `yieldOnEquity`. Реализованная утилизация капитала — измеримый критерий выхода Фазы 1, не только уровни фандинга.

### FM-08. Ротация «в лучшую возможность» без гистерезиса съедает капитал [В]

Одна ротация = 0.31% комиссий + двойной slippage. При медианной длине эпизода 1–2 интервала это плата 31 интервала базового фандинга за долю преимущества в одном.

**Механизм:** претендент обязан обыграть текущую позицию более чем в 2× амортизированного round-trip; жёсткий счётчик минимального удержания в интервалах, навязываемый `risk/` независимо от `strategy/`. Совпадает с FR-303 SRS, уточняет числовой множитель.

### FM-09. Стоимость заимствования USDT сопоставима с валовой доходностью на мажорах [В]

`hourlyBorrowRate` USDT (VIP0, 2026-08-05) = 0.0000044069 → **3.860% APR**. При r=0.010%/8h заимствование съедает 35% валового фандинга; при 0.005% — 71%. Реализованная средняя BTC 2026 YTD = 0.00161%/8h = **1.8% годовых — ниже стоимости заимствования**: каждая пара BTC на заёмном обеспечении в этом году теряла деньги на carry ещё до первой комиссии. Списание — на 5-й минуте каждого часа, невидимо ни в фандинговом реестре, ни в position P&L.

**Механизм:** `r_net = r8h − borrowCost8h`, жёсткое вето при `r_net < minNetFundingRate`. Прямая связь с PARAMS-CONSERVATIVE §11: `isLeverage=0` (см. FM-27) — базовая защита именно от этого канала потерь.

## ТИР 1 — Механика исполнения: сработает на первой же сделке, если не заложить сейчас

### FM-10. Base coin спот-ноги не является обеспечением — либо вовсе, либо с дисконтом [П]

**89 из 293** spot-paired базовых монет отсутствуют в `GET /v5/spot-margin-trade/collateral` целиком (AGI, AIOZ, ALCH, BEAM, BICO, BLAST, BRETT, FIDA, LRC, WAVES, C98, DRIFT, GOAT, MOCA, SONIC и ещё ~74) — ровно неликвидные small-cap'ы, где живёт высокий фандинг.

**Механизм:** whitelist вселенной — пересечение (перп: linear, USDT, Trading) × (спот: пара существует, Trading, `marginTrading == utaOnly`) × (base coin в collateral ladder с первым тиром ≥ `RHO_MIN`), перепроверяемое `risk/` **в момент входа**, не из кэша.

### FM-11. Спот-комиссия на покупку списывается в base coin — структурный недохедж [П, подтверждено документацией]

`/v5/enum`: «Is makerFeeRate positive? TRUE: Side=Buy → base currency». Любой non-VIP платит 0.1% положительным makerFeeRate ⇒ **покупка всегда платит комиссию в base coin**. Если перп сайзится от заказанного qty — пара нетто-шорт на 0.1% нотионала навсегда. На выходе бот пытается продать записанное количество, в кошельке на 0.1% меньше — **продажа отклоняется ровно на той ноге, которую abort обязан закрыть**.

**Механизм:** `perpQty = roundDownToStep(Σ execQty − Σ execFee[feeCurrency==baseCoin], qtyStep)` — никогда от намерения. Спот закрывается по фактическому балансу монеты, никогда по сохранённому количеству входа; перп закрывается через `reduceOnly=true` от `GET /v5/position/list`.

### FM-12. Квантование perp грубее spot на 266 из 293 пар — точный хедж не представим [П]

BTCUSDT: perp шаг 0.001 (≈$65 нотионала), spot шаг 0.000001. На боевом размере $200 (PARAMS-CONSERVATIVE) хедж по BTC сайзится шагами по $65 — **до 32% промаха на этом конкретном размере**. Это прямо бьёт по выбору боевого размера Фазы 4 — см. открытый параметр в SRS §7.

**Механизм:** одна функция сайзинга: нотионал → base qty → округление **вниз до perp qtyStep** → спотовый ордер ровно на это количество. Вето при `(qtyStep/2 × price)/notional > MAX_RESIDUAL_DELTA` (0.005). Для BTCUSDT это минимальная осмысленная позиция ~$6500 — само по себе входной параметр для решения о минимальном размере Фазы 4, и может исключить BTC на боевом размере $200–500 полностью.

### FM-13. `marketUnit` на spot market order неоднозначен на BUY и SELL [П]

Дефолт Buy трактуется **по стоимости** (qty=USDT), если `marketUnit` не указан явно. Обе стороны возвращают success без ошибки при передаче base-количества вместо quote.

**Механизм:** `marketUnit` — обязательное поле внутреннего типа без дефолта; размеченное объединение `{unit:'base',qty}|{unit:'quote',amount}`, невозможно сконструировать неоднозначный ордер.

### FM-14. Symbol mapping не 1:1: множители, токенизированные акции, экспирационные фьючерсы [П]

393 из 686 USDT-перпов вовсе не имеют spot-пары, включая перпы на акции (AAPLUSDT, AMZNUSDT и др. — нехеджируемы на Bybit в принципе). Ровно 12 множительных перпов (1000PEPE, 1000BONK и т.д.) имеют spot-контрагента под неприставочным тикером — хедж 1:1 без учёта множителя даёт ошибку сайзинга в 1000×. `category=linear` содержит 40 LinearFutures с реальным `deliveryTime` — они не платят фандинг, и модель вернёт по ним мусор.

**Механизм:** `config/` держит руками составленную таблицу `(perp_symbol, spot_symbol, contract_multiplier, verified_at)` — это `RSK-01` и `RSK-13` ниже. Startup-валидатор отказывает при нерезолвящейся строке.

### FM-15. Частичные заливки: непрерывное состояние, для которого у машины состояний Фазы 0 есть словарь, но нужен числовой допуск [П]

На всех 293 overlap-парах `perp minOrderQty == qtyStep`. Частичная спот-заливка 0.0007 BTC легальна, но валидного перп-ордера, хеджирующего именно её, не существует: 0 убирает хедж, минимальный шаг перехеджирует на 43%.

**Механизм:** дополняет `LEG1_PARTIAL`/`LEG2_PARTIAL`/`CLOSE_PARTIAL` в машине состояний ([ARCHITECTURE.md](ARCHITECTURE.md) §4) числовой полосой допуска hedge-ratio, ограниченным бюджетом добора (N попыток, M bps) и жёстким разворотом при недостижении к дедлайну. `MIN_POSITION_NOTIONAL = max(perp minNotionalValue, spot minOrderAmt) × 3` и пол в ≥10 perp-шагов нотионала.

### FM-16. Атомарного кросс-категорийного примитива не существует — нужна durable PairIntent [П]

`create-batch` требует единственный `category` на запрос — spot и linear физически не могут быть в одном запросе; батч неатомарен.

**Механизм:** durable машина `PairIntent` в `execution/` с состояниями из ARCHITECTURE.md §4. `orderLinkId` и целевое qty пишутся в БД **с fsync до первого REST-вызова**. С намерением хранится абсолютный `hedge_deadline_ms`; watchdog, **не находящийся на пути размещения ордеров**, гонит истёкшие намерения в abort. Guard в `execution/` отказывается отправлять открывающий perp Sell, если прочитанный с биржи баланс base-монеты не покрывает намеченный qty.

### FM-17. Неопределённое состояние ордера после таймаута [П]

Слепой retry создаёт вторую позицию; слепой отказ оставляет фантомную ногу. Прецедент — Hummingbot #7295: ордер, признанный неудавшимся, залился через ~1с, а retry-ордер залился отдельно через ~4с.

**Механизм:** явное состояние `SENT_UNKNOWN`, единственный законный выход — резолв по идентичности: `GET /v5/order/realtime` → `order/history` → `execution/list`, в этом порядке. **«Не найдено в realtime» классифицируется как INCONCLUSIVE, никогда NEGATIVE** — во время релиза Bybit закрытые ордера UTA доступны только через history, и именно тот инцидент, что породил неопределённость, ломает и резолвер.

### FM-18. Дубликат `orderLinkId`: и ложная ошибка, и ложный «уже размещён» [П]

`110072`/`170141`/`110030` наивно трактуются как отказ ⇒ бот разворачивает ногу 1, пока нога 2 живёт в стакане — сам механизм идемпотентности, сработавший корректно, при неверном прочтении создаёт голую ногу.

**Механизм:** класс `ALREADY_PLACED` — это **claim, подлежащий верификации**, а не факт: запрос по точному `orderLinkId` со сравнением symbol/side/qty. ID безусловно неймспейсится по ноге: `{epoch}-{intentId}-S`/`-P`, фиксированной ширины, ≤36 символов `[A-Za-z0-9_-]`.

### FM-19. Rate limits: reconciler съедает бюджет и глушит abort-путь [П]

Превышение IP-лимита (600/5с) даёт 403 и **10-минутный полный бан** — возможно с одноногой позицией. Reconciler вызывает тот инцидент, который существует, чтобы его обнаруживать.

**Механизм:** единый token bucket с приоритетом `CLOSE > OPEN > RECONCILE > ANALYTICS`, зарезервированная полоса только для cancel/close/reduceOnly. 403 → жёсткий 10-минутный cooldown, **никогда retry**. WS остаётся живым при мёртвом REST — отдельные лимиты, `wss://stream.bybit.com/v5/trade` как независимый транспорт для ордеров.

### FM-20. Дрейф часов VPS убивает всё, включая abort-путь [В, но при срабатывании — с открытой позицией]

Правило подписи: `server_time − recv_window <= timestamp < server_time + 1000`. Допуск **жёстко +1000мс, `recv_window` его не расширяет** — стандартный совет «увеличь recv_window» на спешащих часах не чинит ничего. Публичные данные продолжают течь, heartbeat идёт — а все приватные вызовы, включая abort, мертвы.

**Механизм:** chrony со slew на VPS. Startup-gate: отказ при `|local − server| > 500мс` от `GET /v5/market/time`. Все таймауты и дедлайны читают **монотонный** источник (`process.hrtime.bigint()`), не wall clock — иначе шаг NTP делает `hedge_deadline_ms` вечным или мгновенно истёкшим.

### FM-21. API-ключ: истечение, IP, права, окружение [П по истечению — дата известна уже сегодня]

С февраля 2026 IP-whitelist правится только через браузер — восстановление принципиально не автоматизируемо, это сценарий «3 часа ночи, нужен человек за десктопом» (совпадает с RR-06 SRS). Успешное чтение баланса **не доказывает** право на торговлю.

**Механизм:** ежечасный authenticated canary — активная проверка права на торговлю (отмена несуществующего `orderLinkId`, ожидание `110001`, не permission-ошибки) **по обеим категориям отдельно**. Self-check собственного egress-IP при старте и каждые N минут, алерт **до** первого `10010`. Дата истечения ключа в конфиге с обратным отсчётом, алерт за 14 дней.

### FM-22. WebSocket: пропущенные филлы, дубли, тихий сталл [П]

Реплея и resume-токена в приватных стримах V5 нет. Регрессия `ws@7.5.12` закрывает **любое** соединение ровно после 16384 data-фреймов кодом 1008 (безопасны 7.5.11 и 8.21.1+). Особо коварно: бот реконнектится каждые несколько минут, «нет данных T секунд» **не срабатывает никогда**, потому что данные между реконнектами идут.

**Механизм:** WS — исключительно ускоритель латентности и hint, **никогда реестр**. Дедлайн abort стартует от монотонных часов в момент отправки ордера, не от полученного события; параллельно идёт REST-поллинг конкретного `orderLinkId` независимо от WS. **Каждый реконнект безусловно ставит в очередь полный REST-resync**, торговля заблокирована до его завершения. Дедупликация филлов по `execId` через UNIQUE-констрейнт БД. `seq` **не** идентичность (Bybit: разные символы могут иметь одинаковый seq). Все транзитивные зависимости пиннятся lock-файлом, CI ассертит версию `ws` вне диапазона 7.5.12.

### FM-23. У спот-ноги нет position-объекта — «биржа источник истины» не выполняется наивно [П]

`GET /v5/position/list` поддерживает только linear/inverse/option. Единственная истина по споту — баланс монеты в `wallet-balance`, смешивающий хедж с пылью, аирдропами, стейкингом, остатками прошлых разворотов. Сравнение на равенство даёт либо постоянные ложные HALT (после которых оператор отключает проверку — и это и есть настоящий отказ), либо пропуск реальной недостачи.

**Механизм:** per-coin ledger, атрибутированный по неймспейсу `orderLinkId`, из `execution/list?category=spot`. Инвариант — **пол, не равенство**: `walletBalance[coin] >= attributed[coin] − dust`. Падение ниже — HALT + закрытие перп-ноги.

### FM-24. Числовые поля — строки, форматирование непоследовательно, схема не валидируется [П]

Одно и то же отношение обеспечения приходит и как `'0.6'`, и как `'0.60'` — строковое сравнение тихо расщепляет одинаковые значения. `maxQty=''` означает «бесконечность»; распарсенное как 0, оно превращает безлимитный тир в нулевой. Типы SDK дрейфуют от живого API (bybit-api #512, #516).

**Механизм:** типизированный codec-слой на границе: runtime-схема, утверждающая присутствие и тип **ровно тех** полей, которые использует бот. Провал схемы — событие уровня kill-switch, не warning. Сравнения денежных полей только через Decimal, никогда строковым равенством.

## ТИР 2 — Редко, но катастрофично: здесь теряются реальные деньги, не комиссии

### FM-25. Ликвидация в UTA Cross Margin — на уровне СЧЁТА, продаёт спот-обеспечение [Р, катастрофа]

«When MMR reaches 100%, margin assets will be sold to settle all liabilities», сокращая «the position that can most reduce the MMR until it reaches 90%». **Правило «25% в одну монету» даёт диверсификацию возможностей и ноль изоляции риска** — одна плохая пара форс-закрывает и здоровые дельта-нейтральные позиции, сбрасывая их спот-ноги по рынку в каскаде. Сам движок ликвидации **создаёт** голую дельту — он не закрывает ноги парами.

**Механизм:** kill switch срабатывает по **`accountMMRate` счёта**, не по дельте и не по per-position `liqPrice`. Жёсткий потолок `ACCOUNT_MMR_MAX` (старт 0.30), симуляция пост-трейд MMR через выделенный эндпоинт Bybit (2025-02-18) перед каждым входом. Триггер уровня 2 на `ACCOUNT_MMR_ALARM` (старт 0.50). **Дополняет RR-19/RR-20 SRS новой обязательной метрикой вместо/вместе с формулой «номинал шорта / equity».**

### FM-26. Асимметрия haircut'а обеспечения: маржа течёт на РОСТЕ цены при нулевой дельте [В]

Прирост спот-эквити зачисляется по ρ<1, нереализованный убыток шорта дебетуется в USDT по 100%. `p_liq = (ρ−MM)/(MM+1−ρ)`: при ρ=0.8, MM=0.025 → +344%; опасны только нижние тиры (ρ=0.4 → ~+60%). Отрицательные балансы по умолчанию идут по коэффициенту 100%.

**Механизм:** ρ берётся из `GET /v5/spot-margin-trade/collateral` (маржинальный обход тиров), **никогда** скалярное `collateralRatio` из `/data` (расходятся для 175 из 240 монет). Вход отклонён при `p_liq < PRICE_HEADROOM` (+100%). Пересчёт каждый цикл сверки.

### FM-27. Auto-Borrow: правило плеча нарушается биржей без единой ошибки [В]

Триггер — не только нехватка свободного USDT, но и **«Unrealized losses from Perpetual or Expiry contracts»** — то есть срабатывает на дельта-нейтральной паре каждый раз, когда шорт уходит в минус. Ошибки нет — ордер просто исполняется за счёт займа, реальное плечо тихо превышает потолок. Ручное погашение недоступно с 4-й по 5:30-ю минуту каждого часа.

**Механизм:** пояс и подтяжки. `spotMarginMode=='0'` — startup-assertion. `isLeverage=0` захардкожен в билдере спот-ордера без возможности переопределить конфигом. Pre-flight: живой свободный USDT ≥ требуемая сумма × (1+buffer). `reconciliation/` каждый цикл ассертит `Σ borrowAmount == 0` — ненулевое значение **жёсткий триггер уровня 2**, не warning.

### FM-28. ADL закрывает прибыльную короткую ногу, оставляя голый лонг [Р, катастрофа]

Верная формула для Cross/Portfolio Margin: прибыль → `PnL(%) × Account MMR`; убыток → `PnL(%) / Account MMR`. **Ранг общесчётный** — бот, соблюдающий низкое плечо, ранжируется низко, но добавление одной несвязанной высокомаржинальной позиции поднимает ADL-ранг всех прибыльных шортов на счёте. Дельта уходит с 0 на +100% нотионала **без единой ошибки в коде и без сигнала в собственном order flow**.

**Механизм:** дополняет FR-305 SRS. Pre-entry вето по `insurancePnlRatio == '-1'` (shared pool, безопасный тир) — `ALLOW_ISOLATED_INSURANCE_POOL=false` по умолчанию. Живой мониторинг `pnlRatio` (не `balance` страхового пула — он с 2025-12-18 обновляется T+1, показывает вчерашнее число во время каскада). Немедленная реакция на `cancelType ∈ {CancelByPrepareAdl, CancelAllBeforeAdl}`. Пост-фактум: любое изменение размера позиции, не атрибутируемое `orderLinkId` бота, — событие уровня kill-switch.

### FM-29. Делистинг любой из двух ног — принудительное закрытие без единого упавшего вызова [В на альтах]

Перп форс-закрывается по средней index price за 30 минут до делистинга; спот-нога **не тронута** → мгновенный недобровольный голый лонг. Обратный случай (делистинг спота) хуже: выводы приостанавливаются, конвертация «expected to take 6 months», а ключ намеренно не имеет права Withdrawal — бот не может воспользоваться путём спасения, даже обнаружив событие.

**Механизм:** `market-data/` пишет строку `symbol_spec_change` на любой диф в `status`/`deliveryTime`/`fundingInterval`. Вето на вход при `deliveryTime != '0'` или `status != Trading` на любой ноге. Прямая связь с AR-02 ниже.

### FM-30. Double fault: unwind ноги 1 тоже падает [Р, но именно здесь теряются деньги]

Обычно по общей первопричине (403, clock skew, maintenance) — голая нога живёт всё время жизни первопричины: 10+ минут при бане, неограниченно при maintenance.

**Механизм:** лестница эскалации в разных доменах отказа — backoff на отдельном HTTP-клиенте → `cancel-all` + market `reduceOnly` нарезкой → kill-switch уровня 1 → фейловер на WS trade endpoint → пейджинг человека по двум каналам с точными `orderLinkId`/symbol/qty для ручного закрытия. Тихой сдачи не бывает.

### FM-31. Kill switch не может закрыть позицию рыночным ордером: `maxMktOrderQty` меньше `maxOrderQty` на 778 из 794 инструментов [В]

BTCUSDT: `maxOrderQty` 1500, `maxMktOrderQty` **150** — десятая часть. Аварийное закрытие отклоняется или молча урезается в единственном сценарии, ради которого механизм существует.

**Механизм (СПРОЕКТИРОВАНО, ЕЩЁ НЕ ПОСТРОЕНО):** `maxMktOrderQty` должен читаться per-symbol при старте, каждое аварийное закрытие должно нарезаться на куски, уважающие этот кап. Сегодня в `src/` нет ни одной ссылки на `maxMktOrderQty` и вообще нет кода размещения ордеров, который можно было бы нарезать — `client.ts` пока read-only (ADR-002, [DECISIONS.md](DECISIONS.md)). Ручных тренировок kill switch на позиции, намеренно превышающей кап, **не проводилось** — проект ещё ни разу не размещал реальный ордер, нарезать аварийное закрытие не на чем.

### FM-32. Position mode / `positionIdx` / `reduceOnly`: «закрытие» открывает вторую позицию [В]

В hedge-режиме Buy без `reduceOnly` открывает новый лонг вместо закрытия шорта — abort-путь удваивает гросс-экспозицию, а бот логирует успешное закрытие. Такие отклонения **не создают записей в order history** — пост-фактум аудит видит чистый лог и пропавшую позицию.

**Механизм:** position mode и margin mode читаются при старте **и на каждом цикле сверки**, отказ при несовпадении с конфигом. `positionIdx` отправляется явно всегда; `reduceOnly=true` на каждом закрывающем ордере, верифицируется чтением `position/list`, не доверием к ack.

### FM-33. Крах между ногами до fsync намерения; два процесса на одном ключе [В]

Если БД пишется после POST — ордер существует на бирже с `orderLinkId`, о котором перезапущенный процесс никогда не слышал. Два процесса оба видят «позиции нет» и оба открывают — «биржа источник истины» здесь не спасает: биржа рапортует агрегат, не намерение.

**Механизм:** намерение пишется с `fsync до` HTTP-отправки; клиент ордеров принимает только персистированный `IntentRow`, размещение без него невозможно по типам. Singleton: `flock` + advisory lock Postgres + **fencing epoch**, вшитый в каждый `orderLinkId`, выводимый при старте из `max(db_max, exchange_max) + 1` — restore-safe by construction. Дополняет RR-17 SRS конкретным механизмом.

### FM-34. Kill switch: внутри main loop / не переживает рестарт / отменяет ордера, но не флэттит / глотает исключение [Р, но обесценивает весь дизайн]

Пять независимых способов, которыми "рубильник" может не сработать, при этом выглядя рабочим: (а) синхронная операция блокирует event loop, unbounded retry, deadlock пула БД — единственный механизм для «всё остальное отказало» отказывает ровно в своём сценарии; (б) `Restart=always` без сохранённого HALT-состояния возвращает бота в чистое состояние, и он возобновляет торговлю в объявленном небезопасным состоянии — **всё остальное в дизайне стоит ниже по течению от этого**; (в) `cancel-all` отменяет только ордера — оператор дёргает рубильник, считая себя плоским, и остаётся с обеими ногами (Bybit DCP как «биржевой эквивалент» недоступен обычному клиенту и тоже закрывает только ордера, не позиции); (г) `cancel-all` возвращает нераспознанный `retCode` или JSON меняет форму — kill switch рапортует «останавливаюсь», останавливается, позиции открыты, оператор считает себя плоским; (д) один булев флаг, гейтящий вход, по неосторожности гейтит и reconciler, и unwind — восстановимое одноногое состояние становится постоянным; (е) флаг-файл не читается: путь отличается dev/prod, относительный путь резолвится от неожиданного cwd, ФС read-only, диск полон.

**Механизм:** дополняет RR-31..RR-38 SRS. Kill switch — **отдельный OS-процесс** с собственным PID, HTTP-клиентом, соединением к БД; **не содержит ни одного открывающего пути** и участвует в fencing epoch (FM-33). Два независимых переключателя: `HALT_NEW` и `FLATTEN_ALL`; reconciler и все закрывающие/reduceOnly-пути **явно исключены** из `HALT_NEW`, и это исключение оформлено тестом. HALT персистится строкой в БД **и** флагом на диске, проверяется до любого биржевого вызова, снимается только явной командой оператора с записью кто/когда/почему; `Restart=` **не** `always` (ADR-005 уже фиксирует `RestartSec=30`/`StartLimitBurst`, это тот же принцип). Успех **никогда не выводится из потока управления**: пишется строка `killswitch_run` с финальным `exposure_open`, выведенным из свежих `position/list`+`wallet-balance` после действия, а не из факта, что запрос на отмену не упал. `cancel-all` ack «indicates acceptance only» — терминальность подтверждается опросом, «позиция не существует» — терминальный успех после подтверждающего чтения `position/list`, не retryable.

**Startup self-test обязателен, не опционален:** абсолютный путь флага резолвится и логируется при старте и на каждой проверке; self-test создаёт флаг, проверяет обнаружение, удаляет, проверяет прекращение — и процесс **отказывается начинать торговлю при провале self-test**. Остановившийся счётчик проверок сам является триггером (fail-safe: молчание watchdog'а — это не «всё в порядке», это неизвестность, которая должна тревожить). Lint-правило запрещает голый `catch` в модуле `killswitch/` — проглоченное исключение именно здесь обесценивает весь остальной дизайн проекта.

**Эскалация при отказе, по нарастающей грубости — СПРОЕКТИРОВАНО, ЕЩЁ НЕ ПОСТРОЕНО:** `cancel-all` по категориям → перечислить живые позиции → `reduceOnly` market-закрытия нарезкой (см. FM-31, лимит `maxMktOrderQty`) → продать атрибутированный спот напрямую. Супервизор не должен останавливаться ни на одном исключении внутри этой лестницы — переходит на следующую ступень, пока либо не подтверждено «плоско», либо не потребовалось ручное подтверждение оператора. **Сегодня ни один из этих шагов не выполняется автоматически.** `src/killswitch-listener.ts` собственным комментарием в начале файла фиксирует явно: «Scope today: this process can raise/clear HALT_NEW and FLATTEN_ALL... It cannot yet actually flatten anything on the exchange — there is no execution/ order placement wired up, no Trade-permission key.» На практике `FLATTEN_ALL` сегодня — это только флаг в БД и на диске плюс алерт в Telegram; **автоматического закрытия позиций на бирже не происходит**, всю лестницу выше оператор обязан выполнить вручную сам.

### FM-35. Поздний филл после abort; PostOnly превращает ограниченный риск в неограниченный [В]

Бот развернул ногу 1, посчитав ногу 2 упавшей, а исходный ордер ноги 2 потом заливается — голый **шорт** без хеджа, достигнутый через сам abort-путь. С PostOnly окно вообще не ограничено: ордер тихо отменяется при пересечении книги, без ошибки, без филла.

**Механизм:** строгий порядок abort — сначала **отменить**, затем подтвердить отмену запросом и прочитать финальный `cumExecQty`, только затем разворачивать. IOC/FOK на обеих ногах, чтобы ордер не мог висеть.

### FM-36. Ценовые полосы отклоняют ногу ровно в ту волатильность, которая её вызвала [В]

Полосы считаются от последней цены; быстрое движение посреди исполнения отклоняет вторую ногу, а разворот исполняется в рынок, который по определению движется достаточно быстро, чтобы сработала полоса.

**Механизм:** полоса считается локально из `priceLimitRatioX/Y` **до** отправки — отказ до round-trip. Коды полосы (`110003`,`110120`,`110121`, spot `170192-194`) никогда не ретраятся с той же ценой.

### FM-37. Обслуживание Bybit и частичные отказы сервиса [В]

Опасен именно **частичный** случай: спот жив, деривативы нет — вход даёт гарантированно одноногую позицию, abort не может дотянуться до недостижимой ноги.

**Механизм:** `killswitch/` подписан на `GET /v5/system/status`. Никаких новых входов при maintenance `ongoing` или `scheduled` в пределах 30 минут. `maintainType='3'` (инцидент) — автоматический HALT уровня 2.

### FM-38. `emulation/liquidation.ts`: margin-tier заглушка для символов вне fetched-юниверса не консервативна для тонких альтов; `scenarioRunner.ts` не проверяет источник тира [П, подтверждено live-запросом к API]

**ОБНОВЛЕНО — полный-юниверс fetch сделан:** `lookupMarginTier()` больше не падает на заглушку для «всех символов кроме двух». `KNOWN_MARGIN_TIERS` по-прежнему хранит только BTCUSDT (35 тиров) и ADAUSDT (30 тиров) — вручную сверенные с официальными worked-example цифрами Bybit и проверяемые первыми — но под этим слоем теперь лежит `FETCHED_MARGIN_TIERS`, загружаемый из `src/emulation/marginTierData.json` (293 символа, сгенерирован `src/scripts/fetchMarginTierData.ts` со снапшота `GET /v5/market/risk-limit` от 2026-08-05/06). `lookupMarginTier()` консультирует этот слой для любого символа, которого нет в `KNOWN_MARGIN_TIERS`, прежде чем когда-либо упасть на `FALLBACK_CONSERVATIVE_TIER`. Заглушка (2% MMR / 4% IMR) остаётся только последним рубежом — для символа, отсутствующего в обоих слоях (новый листинг после снапшота, дрейф вселенной). Она по-прежнему **выглядит** консервативной на фоне BTCUSDT/ADAUSDT/DOGEUSDT (0.5-0.75% tier-1 MMR у всех троих), но перестаёт быть консервативной именно там, где это важнее всего: живой запрос к `/v5/market/risk-limit?symbol=ESPORTSUSDT` во время верификации 2026-08-06 показал tier-1 MMR **5%** — в 2.5 раза выше заглушки. Для тонкого альта, всё же провалившегося в заглушку, она занижает реальный риск ликвидации, а не завышает.

**Механизм:** ничего в самом `liquidation.ts` не проверяет, действительно ли символ тонкий/малоликвидный — это явно вынесено на PARAMS-CONSERVATIVE.md §4's ликвидити-фильтр как внешнюю зависимость, которую этот файл не обязан (и не может) сам обеспечить. Если этот фильтр когда-либо пропустит малоликвидный альт (баг фильтра, изменение порога, ручной override), и символ к тому же не попал в `marginTierData.json` — `liquidation.ts` для него молча посчитает цену ликвидации по заниженному MMR, что при leverage-сценарии Фазы 2 сдвигает расчётную цену ликвидации дальше от реальной, чем она есть на самом деле.

**Что нужно перед тем как доверять leverage-сценариям Фазы 2 на символах вне BTCUSDT/ADAUSDT:** (а) **сделано** — `GET /v5/market/risk-limit` подтянут для полного торгуемого юниверса (~293 символа) и заменил заглушку реальными тирами через `FETCHED_MARGIN_TIERS`, см. выше. Остаётся (б): `scenarioRunner.ts` уже построен (`src/emulation/scenarioRunner.ts` — тонкий barrel над `./scenarioRunner/{orchestrator,positionLifecycle,candidateSelection,dbReaders,tickProcessing}.ts`), но **сегодня не выполняет саму проверку источника тира** — `candidateSelection.ts` вызывает `lookupMarginTier(symbol, projectedShortNotional)` и передаёт возвращённый тир напрямую в `computeMaintenanceMargin`, ни разу не читая поле `tier.source`. Явный отказ прогонять leverage-сценарий на символе с `source: "conservative-placeholder"` — реальный оставшийся пробел, не гипотетический.

## ТИР 3 — Реально, ущерб ограничен, но каждый пункт требует кода

**FM-38.** Дрейф плеча и концентрации без единого ордера — цена растёт на 60%, гросс 2X→3.2X при неизменном equity. *Механизм:* пересчёт эффективного плеча и концентрации каждый цикл из `positionValue` (mark) против equity; ступень де-риска, подрезающая обе ноги пропорционально.

**FM-39.** Фандинговый дебет — синхронный портфельный маржинальный шок по расписанию (20:00/00:00 UTC для большинства символов), и книга тоньше всего именно тогда, потому что все фандинг-арб-боты разворачиваются в ту же секунду. *Механизм:* проекция маржи за T минут до каждого `nextFundingTime`; де-риск при превышении потолка проектируемого MMR.

**FM-40.** Вход/выход в 5-секундном окне сеттлмента не гарантирует включения. Экономика: $5 на $10k против $30-40 round-trip — при 50% попадании сделка строго отрицательна. *Механизм:* `FUNDING_ENTRY_BLACKOUT_SECONDS` (старт 60), kill switch из этого правила явно исключён.

**FM-41.** Фандинг платится на mark-нотионал в момент расчёта, не на нотионал входа — на падающих рынках, где положительный фандинг держится дольше всего, реализованный доход систематически недобирает. *Механизм:* доход считается по консервативной траектории цены (`ADVERSE_PRICE_ASSUMPTION` −10%).

**FM-42.** Фандинг — отдельная кошельковая транзакция, невидим для position-based учёта; не входит в `unrealisedPnl`. *Механизм:* реализованный фандинг выводится **исключительно** из `GET /v5/account/transaction-log` (`type=SETTLEMENT`), с учётом инвертированного знака поля `funding`.

**FM-43.** Три денежных потока с тремя разными каденциями (комиссии/фандинг/процент по займу) — наивная суточная сверка против дельты кошелька даст постоянный необъяснённый остаток. *Механизм:* сверка с разбивкой по `type` (TRADE/SETTLEMENT/INTEREST/TRANSFER), каждый поток моделируется отдельно.

**FM-44.** Исчерпывающий разбор `execType`/`cancelType` — фильтр `execType=='Trade'` молча выбрасывает `AdlTrade`/`BustTrade`, бот никогда не узнаёт, что биржа закрыла часть шорта. *Механизм:* exhaustive switch с hard error на неизвестном значении; `CancelByAccountBlocking`/`CancelByDelivery` — options-only, строить детекцию на них бессмысленно.

**FM-45.** Self-Match Prevention отменяет собственную вторую ногу, когда выход по символу и вход в него же пересекаются. *Механизм:* per-symbol in-flight mutex в роутере ордеров.

**FM-46.** Ретеншн order history: только последние 24 часа отдают Cancelled/Rejected/Deactivated — после 36 часов простоя отменённый ордер неотличим от «никогда не отправлялся». *Механизм:* `execution/list` (2 года) — решающий оракул: нет записи об исполнении ⇒ доказуемо не было эффекта на баланс.

**FM-47.** Reconciler действует по рваному снапшоту (wallet→position→orders читаются последовательно ~секунду) и торгует против воображаемого дрейфа. *Механизм:* сверка только из quiesced-состояния, расхождение подтверждается на двух подряд тиках прежде, чем становится сделкой.

**FM-48.** Накопление дасти и минимальные нотионалы блокируют abort — остаток после частичного филла может быть ниже spot `minOrderAmt` (варьируется, до 225 у отдельных пар) и не закрывается никогда. *Механизм:* `MIN_POSITION_NOTIONAL` с запасом ×3, терминальное состояние `DUST` с алертом вместо цикла ретраев.

**FM-49.** Переименование тикера/миграция токена посреди позиции (подтверждённые случаи: TON→GRAM, IP→DATA, XION→VERONA) — переименованный символ может существовать только на споте, оставляя расчётный шорт без спот-контрагента. *Механизм:* reconciliation сравнивает полный набор ненулевых балансов монет с набором, который бот считает своим, каждый цикл; нераспознанная монета — жёсткий HALT.

**FM-50.** Конфиг/миграции/drain при деплое: SIGTERM-drain, обрезанный `TimeoutStopSec`, воспроизводит на каждом деплое ровно тот mid-open SIGKILL, от которого защищался весь дизайн. *Механизм:* строгая схема конфига без тихих дефолтов для риск-параметров; миграции только из доказуемо плоского состояния; явный SIGTERM-обработчик → `DRAINING`.

**FM-51.** Telegram — единая точка отказа для команды и алерта одновременно. *Механизм:* дополняет RR-32/RR-36 SRS — минимум три канала (флаг-файл, строка БД, Telegram), недоступность Telegram дольше порога сама триггер уровня 2.

**FM-52.** Улики уничтожаются ротацией логов; непроверенный бэкап — не бэкап. *Механизм:* каждый ордер-мутирующий HTTP-вызов — в неротируемую append-only таблицу `api_calls` с redaction на уровне логгера; квартальные учения восстановления.

**FM-53.** Библиотеке нельзя верить: retry/backoff могут быть декларативными, но не работать (pybit #342 — код числился retryable, но библиотека бросала исключение). *Механизм:* сырые эндпоинты V5, SDK настроен на ноль ретраев, retry-политика своя в `exchange/`.

**FM-54.** Исчерпывающая классификация `retCode` с ХАЛТЯЩИМ default — ключ **(транспорт, код)**, не просто код: `10016` означает разное в HTTP/UTA и WS таблицах.

## ACCEPTED RISKS — механизма в коде не существует

Дополняет §6 SRS.md.

**AR-07 (расширяет AR-01 SRS). Риск контрагента подтверждён прецедентом, не гипотезой.** 2025-02-21 Bybit потеряла 401 347 ETH (>$1.4 млрд) с холодного кошелька — крупнейшая кража в истории крипты, через подмену того, что видели подписанты Safe{Wallet}. Биржа осталась платёжеспособной, но исход был **условным, а не структурным**. *Потолок:* `MAX_EXCHANGE_EXPOSURE` — сумма, которую можно потерять целиком без материального вреда (RSK-59); ручной sweep прибыли по расписанию в RUNBOOK.

**AR-08 (расширяет AR-02 SRS). Делистинг спота: единственная mitigation — ручной вывод, а ключ на это не способен.** Ключ намеренно без права Withdrawal (RR-01) — правильное решение, но оно означает, что бот физически не может воспользоваться путём спасения даже обнаружив событие. *Принимается сознательно как цена RR-01.*

**AR-09. Смерть хоста: биржевой страховочной сетки не существует.** Bybit DCP (`disconnected-cancel-all`) доступен только Ins-клиентам — недоступен для одиночного разработчика — и даже будучи доступен, отменяет только ордера, не закрывает позиции. Резервные стоп-ордера вредны: стоп, закрывающий только перп-ногу, конвертирует нейтральную позицию в голый лонг в худший момент. *Принимается:* открытая позиция без надзора в течение T часов между смертью хоста и реакцией человека. *Ограничивается:* размер экспозиции подобран так, что T часов без присмотра переживаемы (это прямая причина, почему одна позиция и малый боевой размер — не только осторожность, а структурная защита); off-host uptime-монитор (RR-35 SRS).

**AR-10. Ёмкость: капитал будет простаивать, либо фильтр придётся ослабить.** На единственном положительно бэктестящемся пороге (0.020%/8h) живой срез даёт **ноль** квалифицирующихся символов сегодня, 1.5–3 эпизода/год исторически — при том что правило 25% требует ≥4 одновременных позиций. Третьего не дано. *Принимается:* низкая утилизация капитала как ожидаемый режим, не как поломка.

**AR-11. Уникальность `orderLinkId` не имеет документированного окна ретеншна.** «Переотправь тот же ID, ошибка дубликата докажет, что первый дошёл» — корректно только внутри недокументированного окна. *Заменяется:* локальный partial unique index как настоящий мьютекс + ограниченный wall-clock бюджет ретраев, после которого намерение становится `UNRESOLVED` и разрешается только запросом.
