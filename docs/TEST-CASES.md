# TEST-CASES — тест-кейсы

Версия 1.0 · Фаза 0 · вход: [TEST-PLAN.md](TEST-PLAN.md), [RISK-REGISTER.md](RISK-REGISTER.md), [SRS.md](SRS.md)

Формат given/when/then. Пометка **[mock-only]** — кейс невоспроизводим на testnet (требует событий, которые не индуцируются намеренно, например ADL), покрывается только на моках; поведение проверяется логически, не эмпирически. Пометка **[testnet]** — обязателен на реальном контуре, unit-версии недостаточно. Без пометки — обязателен и на моках, и (где применимо) как регрессия на testnet.

Нумерация раздела 1–4 продолжает исследование RISK-REGISTER.md (53 кейса из синтеза), раздел 5 — позитивные и краевые кейсы, требуемые STLC (бриф, раздел 4) и не покрытые исходным негативным банком.

## 1. Сайзинг и представимость (чистые функции, детерминированно)

1. **Given** реальный снапшот instruments-info и диапазон целевых нотионалов по всем whitelist-парам, **when** запускается сайзер, **then** оба количества кратны своим шагам, представимы в spot `basePrecision`, выше обоих минимумов, residual delta ≤ `MAX_RESIDUAL_DELTA` — иначе явный отказ, не приблизительный размер. *(property-based; RSK-07, RSK-08)*
2. **Given** `qtyStep=0.001`, `price=64674`, целевой нотионал $500 (BTCUSDT), **when** вызван сайзер, **then** вход отклонён `RESIDUAL_DELTA_EXCEEDED` (FM-12).
3. **Given** execution-фикстуры `execQty=100, execFee=0.1, feeCurrency='SOL', qtyStep=0.1`, **when** считается размер перп-ноги, **then** результат ровно 99.9, никогда больше нетто-спота. *(property-based по любой валюте комиссии и шагу; RSK-09, FM-11)*
4. **Given** множитель 1000 для 1000PEPEUSDT, **when** сайзится пара, **then** `perp_notional == spot_notional` в пределах допуска; при множителе, отсутствующем в таблице `symbol_pairs`, вход отклонён (RSK-13, FM-14).
5. **Given** spot-пара `minOrderAmt='225'`, perp `minNotionalValue='5'`, **when** предложен нотионал $100, **then** вход отклонён **до** отправки первой ноги (RSK-12, FM-48).
6. **Given** билдер спот-ордера, **when** конструируется market buy без `marketUnit`, **then** код не компилируется / валидация падает (RSK-10, FM-13).

## 2. Атомарность и восстановление

## 5. Позитивные и краевые кейсы

Исходный банк — почти целиком негативный (это ожидаемо: он вырос из каталога отказов). STLC прямо требует позитивных и boundary-кейсов отдельно (бриф, раздел 4) — они добавлены здесь, чтобы «система работает, когда всё идёт по плану» тоже было утверждением с тестом, а не бездоказательным предположением.

### Позитивные (happy path)

54. **Given** валидное намерение входа, прошедшее все проверки `risk/`, **when** обе ноги исполняются полностью и быстро, **then** позиция переходит в `OPEN`, `positions`/`orders`/`fills` заполнены корректно, остаточная дельта в пределах допуска.
55. **Given** открытая позиция и наступление планового сеттлмента с положительным funding, **when** приходит транзакция `SETTLEMENT`, **then** `funding_payments` получает новую строку, сумма соответствует `positionValue × rate` на момент сеттлмента (FM-41, FM-42).
56. **Given** открытая позиция, funding ушёл в минус, **when** цикл `strategy/` следующий раз оценивает выход, **then** намерение выхода создаётся, обе ноги закрываются, позиция переходит в `CLOSED`, итоговый P&L в логе учитывает все четыре ноги комиссий и фандинг (FR-202).
57. **Given** сутки нормальной работы с одной открытой позицией, **when** формируется суточная сводка, **then** она содержит все поля из FR-307 (equity начало/конец, funding, комиссии, чистый P&L, открытые позиции с APR, число входов/выходов, все вето `risk/`, результат сверки, просадка, аптайм), ни одно поле не пусто без явного «нет данных».
58. **Given** штатный плановый рестарт без открытых позиций, **when** процесс поднимается заново, **then** переход `IDLE → RECOVERY → IDLE` происходит без алертов и без блокировки новых входов.
59. **Given** штатный WS-реконнект без потери сообщений (сеть моргнула на доли секунды), **when** восстанавливается соединение, **then** REST-resync подтверждает отсутствие расхождений, `DEGRADED` не наступает.

### Краевые (boundary)

60. **Given** остаточная дельта ровно на границе `MAX_RESIDUAL_DELTA`, **then** поведение на границе детерминировано и покрыто тестом в обе стороны (чуть меньше — принято, чуть больше — отклонено).
61. **Given** funding ровно на пороге входа (0.020%/8ч ± 1 значащая цифра представления Decimal), **then** округление не создаёт недетерминизма между повторными расчётами одних и тех же входных данных.
62. **Given** просадка ровно на границе 3% (RR-20 / PARAMS-CONSERVATIVE §8), **then** триггер срабатывает включительно, а не строго больше — зафиксировать выбранную сторону границы явно и тестом.
63. **Given** позиция размером ровно на границе 25% капитала по номиналу спотовой ноги, **then** вход на границе принят, вход на один минимальный шаг лота выше отклонён (RR-21).
64. **Given** `M` ошибок API подряд ровно на пороге (SRS §2.5, старт M=5), **then** триггер заморозки срабатывает на M-й, не раньше и не позже.
65. **Given** отсутствие данных WS ровно на пороге T (30с) и T2 (300с), **then** переход на REST-поллинг и последующее закрытие происходят на границах, а не с запасом или с опозданием, которые нигде не задокументированы.

## 6. Трассируемость покрытия

Каждый пункт обязательного негативного набора брифа (раздел 4) покрыт (см. таблицу в TEST-PLAN.md §4). Каждый `RSK-nn` из RISK-REGISTER.md имеет минимум один кейс выше — где кейс отсутствовал явно, он добавлен в раздел 5. Пробелов, известных на момент написания, нет; новые пробелы, обнаруженные в процессе реализации Фазы 1+, добавляются сюда же с указанием, каким модулем они были обнаружены, а не оформляются отдельным списком «TODO».

### Ревизия покрытия, 2026-08-06

Полная сверка всех 65 кейсов с реально написанными тестами (не только с существованием файла, а с точным given/when/then). Результат ожидаемый для текущей стадии проекта: подавляющее большинство (46 из 65) требует инфраструктуры, которой намеренно ещё нет — `execution/` реализован только чистыми функциями (машина состояний, `orderLinkId`, классификатор `retCode`, расчёт P&L), реального размещения ордеров, резолвера намерений, WS-потока приватной торговли и лок/эпохи-механизма нет. Это не пробел в тестировании — это честное отражение того, что соответствующий код ещё не написан, писать тест раньше кода бессмысленно.

**Обновление, 2026-08-07**: `reconciliation/` больше не относится к «не существует» — коммиты `4cb492b` и `b36f10b` добавили `src/reconciliation/recoverOnStartup.ts` (решающая логика восстановления после рестарта/краша: `findUnresolvedIntents` — реальный DB-запрос последнего незакрытого намерения на позицию, плюс чистая `decideRecoveryOutcome`, реализующая три задокументированных исхода `IDLE → RECOVERY → {IDLE, OPEN, STUCK_LEG}` из ARCHITECTURE.md §4) и `src/reconciliation/checkInvariants.ts` (все пять инвариантов периодической сверки из ARCHITECTURE.md §4: совпадение счётчика открытых позиций, остаточная дельта RR-15, детекция ADL по FR-305, таймаут зависших `*_SENT`/`*_UNKNOWN` ордеров, потолок leverage/MMR по RR-20/FM-25 — последний делегирует в `risk/leverage.ts`, не дублируя пороги). Обе тестовые сюиты (`test/reconciliation/recoverOnStartup.test.ts`, `test/reconciliation/checkInvariants.test.ts`) написаны: чистая половина (`decideRecoveryOutcome`, все пять `check*`) проходит в любом окружении без внешних зависимостей; DB-читающая половина (`findUnresolvedIntents`, `findOpenPositions`/`findPendingOrders`) размечена как «против реального Postgres» и требует живой БД — падает с connection error там, где её нет (например, в песочнице без поднятого Postgres), и подтверждена зелёной на VPS. Оговорка та же, что и у остального `execution/`: это чистые функции плюс read-only DB-запросы — ни один модуль не вызывается из `trader`/`killswitch-listener`, потому что аутентифицированного Bybit-клиента ещё нет (ADR-002/NFR-11); решающая логика готова и протестирована, живого провода к бирже пока нет.
